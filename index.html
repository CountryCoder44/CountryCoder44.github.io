Where I Started and Where I Am Going

My path into computer science did not start in a classroom. In 2019 I began studying electrical engineering at a community college, and in 2020 I took a full-time role at a small agricultural company, where I taught myself enough embedded programming and web development to automate an aeroponic growing operation. In February 2024 I founded Fireback Software LLC, and that September I went back to school, studying computer science at Middlesex County College. I began the Bachelor of Science in Computer Science at Southern New Hampshire University in May 2025, and alongside it completed a full-stack software engineering bootcamp through Metana, from September 2025 to May 2026. I start a Master of Science in Artificial Intelligence in December 2026.

That order matters to how I see this degree. For most of my career I learned what I needed in order to ship the next thing. The Computer Science program gave me the theory underneath the practice: the vocabulary of algorithmic analysis, formal testing discipline, and secure design principles, so I can explain and defend decisions I used to make mostly on instinct. Building this ePortfolio forced me to do exactly that. Every claim in it had to be backed by evidence I could show someone else, not just by working software.

My goal is to grow from implementing software into owning complete products: the architecture, the technical decisions, and delivery from first idea to real users. That is the work I already do as the founder of Fireback Software, where I build full-stack and AI-powered applications for clients, and it is the standard I want to bring to a permanent engineering role.

Collaborating in a Team Environment

Most of my professional work has happened on small and medium teams, up to about fourteen people, and today I regularly work alongside distributed developers and QA engineers to iterate, test, and release production software. On a 2026 engagement with a smart-hardware client, I owned the touch-interface functionality across four concurrent product pipelines, delivered engineering improvements across more than eleven active products, and supported four to five commercial launches through feature validation, troubleshooting, and release preparation. Work at that scale only succeeds when each person's changes are safe for everyone else, which is why I put so much weight on automated tests, continuous integration, and clear module boundaries. They are what let a team move quickly without stepping on each other.

This program reinforced the human side of that. Preparing a code review for a peer and manager audience in this course made me explain my own code the way I would want a teammate to explain theirs: what it does, where it is weak, and what I plan to change and why.

Communicating with Stakeholders

I have been in direct conversations with company leadership and investors, not only with fellow engineers, and that experience changed how I communicate. An executive wants to know what changed, what it cost, and what risk it removed or introduced. A teammate debugging the same system needs the actual mechanism. I learned to move between those two registers, sometimes in the same afternoon. For a logistics client, I designed and deployed a mobile reporting application that improved reporting accuracy by 27% and automated operational workflows that removed more than 30 hours of manual work per week. Results like those are what a stakeholder hears, and I have learned to lead with them and keep the technical detail ready for whoever needs it.

Data Structures and Algorithms

Before this program I could make software work. The formal study of algorithms and data structures taught me to ask how well it works as the data and the number of users grow. In my Emerging Trends in Computer Science course, I built a deep Q-learning agent that taught itself to navigate a maze to a treasure, using an experience replay buffer of 512 transitions, a separate target network that updated every 50 epochs, and an exploration rate that decayed from fully random toward mostly greedy as the agent improved. It reached a 100% win rate over its final 32 training games. That project made concrete how the choice of data structure, here a replay buffer that let the agent learn from past experience more than once, directly shapes what an algorithm can achieve. I now bring that question to everyday engineering: what does this cost as the input grows, and is there a structure that makes it cheaper?

Software Engineering and Databases

My software engineering started with my own projects. At Microgreens & Micromachines, self-taught at the time, I architected and built an aeroponic cultivation system that was about 80% automated, using Arduino-based embedded controllers in C++ to run nutrient delivery, misting, and environmental controls from sensor-driven logic. I also built the web application that monitored it remotely, with real-time telemetry and automated email and text alerts. The system reached roughly six times the crop yield in the same physical footprint. Building something that had to run unattended, where a failure meant a lost crop, taught me early to design for failure and to watch real behavior instead of trusting that a system works.

The program then gave that experience structure. In Full Stack Development I took a travel booking application from a static Express site to a Model-View-Controller design, then to a MongoDB-backed REST API with a separate Angular single-page application for administrators. In Mobile Architecture and Programming I built a mobile inventory application in Kotlin. Alongside coursework, ChromiTap, a color management application I started as a personal tool, has grown well beyond its original scope into broader creative and productivity tooling that I use in my own UI and UX design work. Managing that growth has taught me as much about product scope and architecture as any single feature has.

Security

I approach security as a habit of asking how something will fail, and what happens to users and their data when it does. In Full Stack Development I added authentication to the travel application's administrator API with JSON Web Tokens, so only authorized users could change its data. In TrakCode, outside the three enhancements in this portfolio, the service that runs learners' code is isolated: it has no internet access, a read-only file system, and no special system privileges, because it exists specifically to run code nobody has reviewed. When I added social sign-in, I wrote a guard against account takeover, so that someone who registered a victim's email address first could not keep a way into that account. I treat privacy the same way: TrakCode encrypts the access tokens it stores for connected GitHub and LinkedIn accounts with AES-256-GCM, and deleting an account removes the learner's code, progress, and conversations with Trak instead of just hiding them. Preparing this portfolio for public release was its own security exercise: I removed every credential, API key, and production server identifier from the code before publishing it.

How the Artifacts Fit Together

The artifacts that follow all come from TrakCode, a full-stack coding education platform I designed and built, and continue to operate, outside of my coursework. Using one real, working system for all three categories, instead of three disconnected class projects, meant every enhancement had to hold up in software real users touch, not just against a rubric.

Each enhancement started from a specific finding in my code review and ended with evidence. In software design and engineering, I restructured the backend so it could be tested, and fixed an AI safety check that failed open instead of closed. In algorithms and data structures, I made problem selection fair and efficient, cached repeated work, and rebuilt a hint system to work correctly across languages, with complexity analysis and measured timings to support each change. In databases, I consolidated duplicated data access, built an integrity check that found 36 real orphaned records in my development database, and moved an expensive check into the database itself, confirmed with the query planner. Together they show the discipline I want an employer to see first: I find out whether my code actually works, and I am honest with myself when it does not. The code review, the original and enhanced code, and a narrative for each enhancement follow.
